01 - Before · Execute, then agree

Execution bounded the round.

Block proposal required the proposer to execute every transaction first; validators re-executed the full payload before casting a vote. Under heavy compute load, execution consumed up to 4.5 seconds of the 6-second round, so time to finality was dominated by computation rather than agreement.

02 - Decoupled · Propose, vote, then execute

From 6 s to 600 ms

The proposer selects transactions and broadcasts the block header and body without executing them. Validators verify the proposal against protocol rules and vote at once. Execution proceeds asynchronously on a parallel path, and its state root and receipts are committed in a subsequent block.

04 - Cross-Cluster · Three shards, one metachain

From ~18 s to ~2.4 s

A cross-cluster operation is finalised on the source lane, notarised by the coordination metachain, then executed on the destination lane. Compressing this path to three steps at 600 ms rounds settles multi-lane payloads in roughly 2.4 seconds.

05 - Safety under load

Bounded
execution lag.

Mempool with virtual state Maintains pending nonces, projected resource consumption, and the set of payloads proposed but not yet executed so proposers only select valid work.
Automatic backpressure When execution lag exceeds a threshold, block capacity adjusts protocol-wide until execution catches up, keeping backlogs bounded without human intervention.
Ordering locked at proposal The proposer commits to the exact sequence before any execution result exists, eliminating outcome-dependent reordering as a manipulation surface.
Deterministic finality One aggregated consensus proof per block. Execution results are committed in subsequent blocks; the agreed ordering is immutable once the proof exists.

07 - What changes for builders

Building against a 600 ms round.

Finality is a consensus proof A transaction is final once the aggregated consensus proof for its block exists, typically within 100–250 ms. Confirmation depth is no longer required.
Execution results follow inclusion Inclusion and execution are separate events. Receipts and resulting state are read from the subsequent block that commits the execution results.
Millisecond timestamps Contracts and services read block timestamps in milliseconds. Time-dependent logic is expressed directly in rounds of 600 ms.
Tight feedback loops Real-time order books, autonomous AI agents, high-frequency telemetry, and reactive applications operate directly on sub-second finality.
